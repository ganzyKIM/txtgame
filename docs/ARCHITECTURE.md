# 구조와 결정 기록

코드를 읽으면 알 수 있는 건 안 적는다. **왜 그렇게 했는지**, **다시 건드리면 깨지는 것**,
**실측해서 얻은 숫자**만 남긴다.

기존 `holdem-plan.md` / `persuade-game-prototype.md` / `gomoku-plan.md`를 이 문서로 합쳤다
(원문은 git 히스토리에 있음 — `git log -- docs/`).

---

## 공통

- Vite + React 19 + TS. 서버는 Supabase(Postgres RPC + Realtime + Auth).
- LLM은 Supabase Edge Function `generate-text` 경유. **크레딧이 0이면 거부**된다.
- **게임 로직은 순수 함수로 분리**한다(`src/game/**`). 이유: 같은 코드를 브라우저(싱글)·
  서버·봇 시뮬·노드 테스트 네 곳에서 재사용하기 위해서. UI는 상태를 그리기만 한다.
- 마이그레이션은 **Supabase 대시보드 SQL Editor에 수동으로 붙여넣어 실행**한다(CLI 접근 없음).
  에디터가 스크립트 전체를 한 트랜잭션으로 돌리므로 **문장 하나가 실패하면 전부 롤백**된다 —
  쪼개서 돌리지 말고 항상 통째로 실행할 것. (이 함정에 두 번 걸렸다: `grant`의 파라미터
  개수 오타, `DEFERRABLE INITIALLY` 오타)
- 배포 = `git push origin master` (Vercel 자동 배포). SQL은 배포와 무관하게 따로 실행해야 한다.

### LLM을 안 쓰는 게임이 절반이다
홀덤·오목은 전부 정해진 로직이라 **운영비 0원**이다. 크레딧 소모처가 아니라 리텐션 담당.

## 멀티플레이 — 게임마다 신뢰 모델이 다르다

세 게임이 서로 다른 구조를 쓰는데, 이건 실수가 아니라 **숨길 정보의 양**이 다르기 때문이다.

| 게임 | 모델 | 왜 |
|---|---|---|
| 퀴즈 대합전 | 호스트 권위 | 최악의 부정이 "호스트가 정답을 미리 안다" 수준 — 판이 깨지진 않음 |
| 홀덤 | **서버 권위(필수)** | 손패가 새면 게임이 즉시 무의미해지고, 칩이 걸려 부정 동기가 큼 |
| 오목 | 서버 검증 + 공개 테이블 | **숨길 정보가 아예 없다** — 판이 양쪽에 다 보임 |

### 홀덤이 서버 권위여야 하는 이유
호스트 클라이언트가 카드를 나눠주면 **호스트가 전원의 패를 본다.** 클라이언트에 내려간
데이터는 콘솔에서 다 보이므로, 상대 패가 조금이라도 클라에 오면 끝이다.
숨기는 방법은 이미 프로젝트에 있던 패턴을 그대로 쓴다: **테이블에 RLS select 정책을 주지
않고**, `security definer` RPC로만 자기 것을 꺼내가게 한다(`mp_rounds`가 원조).

### 오목이 단순해도 되는 이유
착수를 공개 테이블(`gomoku_moves`)에 쌓고 realtime으로 동기화한다. 서버는 차례(착수 수의
홀짝)·빈 칸·방 상태·제한시간·**5목 승리 판정**을 검증하므로 "내가 이겼다"고 주장할 수 없다.
동시 착수 경합은 `unique(room_id, r, c)`와 `primary key(room_id, move_no)`가 DB 레벨에서 막는다.

**단, 렌주 금수만 클라이언트 검증이다.** SQL로 금수 판정을 재구현하는 비용이 커서 감수한
트레이드오프 — 개조 클라이언트는 금수를 둘 수 있다. 지인끼리 두는 캐주얼 게임 기준.
(흑의 장목은 서버 승리 판정이 5목으로 인정하지 않으므로 부분적으로는 서버도 렌주를 반영)

### 타임아웃: pg_cron이 없다
Postgres가 스스로 타이머를 못 돌린다. 그래서 **클라가 타이머 UI를 그리고, 초과 시 아무나
RPC를 부르면 서버가 실제 경과시간을 재검증한 뒤에만** 처리한다(클라 시계를 안 믿음).
오목은 `gomoku_claim_timeout`이 이 역할. 방 정리도 같은 이유로 크론 대신 "로비를 열 때마다
청소"한다(`023_mp_cleanup_no_cron.sql`).

### 멀티 봇 (초텐/아메)
봇은 세션이 없어 `auth.uid()`로 좌석을 못 찾는다. 그래서 **호스트 브라우저가 싱글과 똑같은
엔진으로 수를 계산해 대신 제출**한다(`gomoku_place_as_bot` / `poker_add_bot` 계열).
검증 로직은 사람용과 반드시 같아야 하므로 `gomoku_place_internal`로 뽑아 공유한다.

### 초대 링크
방 화면에서 `?gomoku_room=` / `?holdem_room=` / `?multi_room=` 링크를 공유한다.
모바일은 네이티브 공유 시트, 안 되면 클립보드 복사. 로그인이 필요한 경우를 위해
**OAuth `redirectTo`를 origin이 아니라 현재 URL 전체로** 준다 — 안 그러면 로그인 왕복에
쿼리스트링이 날아가서 어느 방으로 가려던 건지 잃어버린다.

## 오목 (렌주)

### AI는 라이브러리 + 직접 얹은 4가지
[`@algorithm.ts/gomoku`](https://www.npmjs.com/package/@algorithm.ts/gomoku) v4.0.5 (MIT, minimax+alpha-beta).
탐색은 이미 잘 풀린 문제라 직접 짜지 않았다. 라이브러리가 **안 주는 것**을 얹었다:
승리 판정 / 렌주 금수 / 난이도 등급 / 대사 트리거용 상황 분석.

### 색과 역할을 분리한 이유
`Player`(0=흑, 1=백)는 **색**이고, 누가 사람인지는 `humanSeat`이 따로 갖는다.
싱글에서 **판마다 흑백을 번갈아** 잡기 때문에 "사람=흑"으로 굳히면 안 된다.

여기서 중요한 함의: **금수는 언제나 흑에게 걸리므로 AI가 흑이면 AI도 금수를 지켜야 한다.**
라이브러리는 금수를 모르고, 삼삼은 순수 오목에선 오히려 강수라 탐색이 적극적으로 고른다.
그래서 고른 수가 금수면 그 칸을 **"상대 돌이 있다"고 속여 배제하고 재탐색**한다(최대 8회).

### 렌주 판정
흑만 제약: **장목**(6목 이상) 금수 → 흑은 정확히 5목만 승리 / **사사**(4-4) / **삼삼**(3-3).
**5목 완성은 금수보다 우선**(이기는 수는 언제나 합법).

> 열린3의 정의에 **"4가 아니면서"** 를 빼먹으면 합법인 **사삼(4-3)이 삼삼으로 오판**된다.
> 실제로 있었던 버그. 테스트로 잡았다.

정식 렌주의 재귀적 금수 판정(그 3을 4로 키우는 수가 그 자체로 금수인 경우)은 안 한다 —
캐주얼 구현 관행.

**UX**: 정식 렌주는 금수를 두면 즉시 패배지만, 모르고 클릭했다 지면 납득이 안 된다.
그래서 금수 자리를 판에 **✕로 미리 표시**하고 착수를 거부하며 캐릭터가 이유를 말한다.
전수 계산이 실측 1ms라 매 착수마다 다시 구한다.

### 난이도 — 깊이만으론 등급이 안 나온다
깊이를 낮춰도 AI가 4목을 다 막아서 초보가 못 이긴다. 그래서 **실수율(blunder)** 을 넣었다.
단 "지금 두면 바로 이기는 수"는 절대 안 버린다 — 다 이긴 판을 놓치면 버그처럼 보인다.

| 난이도 | narrow | deepDepth | 실수율 | ponderMs | 결정적 차단 실패율(실측) |
|---|---|---|---|---|---|
| 살살 | 2 | 6 | 35% | 0.7s | 31% |
| 보통 | 2·4 | 12 | 12% | 1.0s | 11% |
| 진심 | 2·4·8 | 16 | 0% | 1.3s | 0% |

자기대국 라운드로빈(각 20판): 진심>보통 85%, 진심>살살 100%, 보통>살살 100%.

**ponderMs가 왜 필요한가**: 탐색이 대부분 **1ms**에 끝나서 "생각도 안 하고 착착 놓는" 느낌이
난다. 난이도별 최소 대기를 준다.

### Web Worker
탐색이 동기라 길어지면 메인 스레드가 막힌다. `aiWorker.ts`로 분리(생성 실패 시 동기 폴백).

> **측정 정정**: 초기 "한 수 최악 12초"는 자기대국 하네스가 색을 잘못 다뤄(흑 차례에 백 수를
> 계산) 만든 비정상 국면 탓이었다. 고친 뒤 진심 40판에서 **한 판 전체 최대 1.5초**.
> 그래도 워커는 유지 — 막히면 탭이 죽은 것처럼 보이는 리스크가 크다.

### 검증 (노드 테스트, esbuild 번들 후 실행)
엔진 42건 / 렌주 25건(사삼 합법 포함) / AI 흑 금수 준수 5건(흑 착수 319회 위반 0건) /
난이도 서열·차단 실패율 / 멀티 대사 매핑 5건.

## 홀덤

### 엔진이 크라운 주얼
`reduce(state, action)` 순수 함수. **엔진은 누가 사람이고 봇인지, 싱글인지 멀티인지 몰라야
한다** — 그래야 싱글 클라·서버·봇 시뮬·테스트 네 곳에서 재사용된다.
버그의 온상은 **사이드팟·동점(kicker)·최소 레이즈** 세 곳이라 테스트를 여기 집중했다.

### ⚠ 겜블링 경계 — 타협 불가
이 프로젝트의 크레딧은 **운영자가 부여하는 재화**이고 실제 현금 구매 경로가 없다.
그 전제 위에서만 아래가 성립한다. **크레딧에 실결제 경로가 생기면 이 설계 전체를 재검토해야 한다.**

- 놀이용 칩은 크레딧과 **별개 잔고**. **칩→크레딧 환전 경로를 만들지 않는다**(편도 구매만).
- 구매는 **서버가 고정한 환율로만** — 클라가 금액을 요청할 수 없다(`poker_buy_in`).
- 소량만 소요(입장 의식 수준).
- 랭킹은 칩 액수가 아니라 "승리 핸드 수" 같은 게임 지표로 — 칩 액수 경쟁은 도박적 동기를 자극한다.

### 화면은 전신 캐릭터가 주인공이다
좌석 아바타를 130×88로 **잘라서 머리만** 보여주고 있었다. 400×658 전신을 통째로 보여주도록
바꾸면서 레이아웃 규칙이 몇 개 생겼다.

- **상대 좌석 줄이 남는 세로를 전부 가져간다**(`flex:1`). 보드·내 좌석·조작부가 고유 높이를
  먼저 확보하고 나머지를 캐릭터가 채우므로, 아래 UI가 커져도 캐릭터가 줄어들 뿐 **스크롤이
  구조적으로 안 생긴다.** 고정 `clamp()`로 잡으면 아래가 커질 때마다 다시 맞춰야 한다.
- 이름표·핸드는 그림 **아래에 쌓지 않고 위에 겹친다**. 아래에 쌓으면 그 높이만큼 그림 몫이
  깎인다. 말풍선만은 좌석 위 전용 띠(`padding-top`)에 띄운다 — 겹치면 얼굴을 가린다.
- 겹치기는 `:has(.holdem-human-avatar)`로 **캐릭터 좌석에만** 건다. 멀티의 사람 좌석(이니셜
  원)과 내 좌석은 종전 레이아웃 그대로다.
- 캔버스 리샘플러는 **없앴다**. 130px 박스 시절엔 축소 품질 때문에 필요했지만, 지금은 표시
  크기가 원본에 가까워서 작은 축소본을 다시 확대하면 오히려 흐려진다.

### 아래 조작부는 고정 영역이다
차례가 넘어갈 때마다 "액션 버튼 / 상대 차례 안내 / 결과 박스"가 서로 갈아끼워지면서 높이가
달라져 **위쪽 좌석까지 통째로 출렁였다.** 셋을 `.holdem-bottom` 한 슬롯으로 합치고 **전부 항상
그린 뒤 쓸 수 없을 때는 `disabled`만** 준다. 상태 줄·쇼다운 줄은 `min-height`로 빈 상태에서도
자리를 지킨다. 실측 결과 세 상태 모두 **165px 고정**.

싱글과 멀티가 같은 구조였으므로 양쪽 다 고쳤다 — 멀티가 남의 차례가 잦아 더 심했다.

## 캐릭터 이미지 자산 파이프라인

`public/char/*.png`(400×658, 알파)는 전부 **생성 → 배경 제거 → 드롭섀도우** 세 단계를 거친다.
자산은 사람이 골라서 커밋한다 — 런타임 생성은 안 한다(볼 때마다 과금·지연·결과 불일치).

### 생성은 제미나이 **채팅**으로 한다 (API 아님)
구독 중인 채팅 창을 쓴다. `tools/gen-char.mjs`(API 경로)는 남겨뒀지만 **쓰지 않는다.**

문제는 첨부였다. 제미나이는 "파일 업로드" 메뉴를 누르는 **그 순간에** 숨은
`<input type=file>`을 만들고 즉시 `.click()`해서 OS 파일 창을 연다. 그래서 드롭·붙여넣기
이벤트는 전부 무시되고, 미리 찾아둘 DOM 노드도 없다. 해법:

1. `HTMLInputElement.prototype.click`을 가로채, `type=file`이면 OS 창을 열지 않고
   준비해둔 `File`을 `.files`에 넣고 `change`를 쏜다.
2. 그 `File`은 페이지에 따로 심어둔 내 `<input type=file>`에 확장 도구로 넣어 조달한다.
3. 이후 "+ → 파일 업로드"를 누르면 레퍼런스가 첨부된다.

레퍼런스 없이 텍스트로만 시키면 **캐릭터가 완전히 다른 사람이 된다**(대화가 길어질수록 심함).
한 캐릭터당 채팅 하나를 파고, 첫 턴에 레퍼런스를 붙인 뒤 표정 변형은 후속 프롬프트로 잇는다.
생성은 한 장에 **2~12분**이고 8분쯤에서 실패로 끝나기도 한다 — 실패하면 그냥 다시 보낸다.

### 크로마 배경은 캐릭터마다 달라야 한다
`tools/cutout.mjs`는 색이 아니라 **연결성(flood fill)** 으로 지운다. 그래도 배경색이 캐릭터
팔레트와 겹치면 무너진다.

| 캐릭터 | 배경 | 왜 |
|---|---|---|
| 초텐쨩 | **파랑** `#0000FF` | 마젠타는 분홍 리본과 색조가 겹쳐 **머리카락이 투명하게 뚫렸다**. 초록은 민트 머리를 지운다 |
| 아메 | **초록** `#00FF00` | 검정·진홍 팔레트에 초록이 없다 |

같은 이유로 **스필 보정 세기도 배경색이 정한다**(`domCh === 1`, 즉 초록일 때만 과감하게).
초록은 두 캐릭터 팔레트에 없으니 "초록이 제일 높은 픽셀 = 스필"로 봐도 안전하지만,
마젠타·파랑은 분홍 피부·빨간 나비넥타이·연한 하늘색과 겹쳐서 그렇게 누르면 색이 죽는다.
실제로 마젠타 배경에서 **빨간 나비넥타이가 통째로 배경 취급되어 지워졌다.**

> 살아남은 픽셀 비율로 자동 판정하는 것도 해봤는데, 두 캐릭터 수치가 겹쳐서(6~11%) 못 갈랐다.
> 배경색으로 직접 가르는 쪽이 정확하고 짧다.

### 프레이밍은 프롬프트로 강제해야 한다
"10% 여백" 정도로는 무시당해서 토끼 귀가 잘렸다. **"귀 끝이 위 가장자리에서 한참 아래,
신발이 아래 가장자리에서 한참 위, 어떤 것도 가장자리에 닿지 말 것"** 처럼 구체적으로 쓴다.

## 설득게임

**LLM의 자기신고를 믿지 않는다**가 핵심 원칙. 게이지 변화량은 `clampDelta`로 범위를 강제하고,
비밀 누설은 `leakedSecret`으로 코드가 직접 검사한다. 파싱 실패·누설 시 폴백 대사로 대체.

Mascot 컴포넌트를 고치지 않고 **가벼운 전용 도킹 컴포넌트를 새로 만들었다** — 떠다니는
마스코트와 화면에 박힌 캐릭터는 요구사항이 달라서 한 컴포넌트에 욱여넣으면 둘 다 나빠진다.

## 마스코트 대사

- 데이터(`src/game/mascotLines.ts`)와 타이밍(`Mascot.tsx`)을 분리했다.
- **캐릭터가 화면의 일부인 곳에서만 치운다**(`banish`): 홀덤 테이블, 설득, 오목 싱글.
  **멀티에서는 관전자로 남아 응원한다** — 퀴즈 대합전이 원조 패턴이고 오목 멀티도 여기 맞췄다.
- 멀티 대사(`omok_mp_*`)는 싱글 대사(`omok_*`)와 시점이 반대다. 싱글은 "마스코트=상대",
  멀티는 "마스코트=내 편". 그래서 재사용하지 않고 따로 썼다.
- 오목 멀티에서 상황 판정은 싱글 엔진(`applyMove`)을 재사용하되 `humanSeat`을
  `opponentOf(mySeat)`로 **뒤집어서** 부른다 — 그러면 `ai_threat`가 곧 "내가 만든 위협"이 된다.
- `event()`가 끝날 때 앰비언트 타이머를 리셋한다. 안 그러면 대국 중에 "퀴즈 하자"가 끼어든다.

### 의상(costume)은 마스코트에만, 홀덤 바니는 좌석 이미지로
`Costume`(현재 `kimono` 하나)은 **떠다니는 마스코트**의 이미지 경로를 통째로 갈아끼우는
장치다. 오목 화면이 이걸 쓴다(`setCostume('kimono')`).

홀덤의 바니 의상은 **여기 안 들어간다.** 홀덤은 마스코트를 `banish`하고 캐릭터를 좌석에
앉히므로, 갈아끼울 대상이 애초에 없다. 그래서 좌석 표정 함수(`botExpression` / `botFace`)가
파일명 접미사를 직접 돌려주는 방식이다.

| 접미사 | 홀덤 상황 |
|---|---|
| `_bunny` | 기본 |
| `_bunny_smirk` | 올인 / 내 차례 / 판 중 능글맞은 반응 |
| `_bunny_contempt` | 폴드, 패배, 판 중 분한 반응 |
| `_bunny_joy` | **승리 시에만** — 아껴야 승리의 상징으로 읽힌다 |

두 캐릭터가 같은 검정 바니면 구분이 안 돼서 **초텐은 빨강 의상·빨간 귀·흰 스타킹**,
아메는 검정으로 갈랐다.

## 알려진 제약

- 오목: 무르기 없음. 싱글 AI는 사람이 흑일 때 그 금수를 전략적으로 이용하지 못한다
  (라이브러리가 렌주를 모름 — 반칙은 안 나므로 정합성 문제는 아님).
- 멀티 전반: 브라우저 2세션 실플레이 검증을 자동화하지 못했다(로그인 게이트). 유저 실측 의존.
- 홀덤 화면 검증도 같은 이유로 **실제 CSS를 읽는 정적 하네스**로 했다(칩 구매에 인증이 필요).
  레이아웃 수치는 그걸로 재고, 실플레이는 유저 확인에 의존한다.
- 창 상단 "처음으로"는 **그 게임의 첫 화면으로** 간다(카테고리 화면이 아니라). 이미 첫 화면이면
  버튼 자체를 숨긴다 — 각 게임이 `onAtHomeChange`로 알려주고 App이 판단한다.
- `docs/mascot-dialogue-reference.json`은 **오래된 스냅샷**이다(이식용으로 뜬 것).
  `mascotLines.ts`와 76%만 일치하고 캐릭터명도 옛 표기("천사쨩")다. 쓰기 전에 재생성할 것.
- `WordChainGame.tsx`와 `PersuadeGame.tsx`는 완성 전이라 **App.tsx에 데스크탑 아이콘을
  일부러 붙이지 않았다**(데드코드도 버그도 아님). 진입 경로가 없다고 "고치지" 말 것 —
  실제로 한 번 그렇게 잘못 판단해서 설득게임 아이콘을 붙였다가 되돌렸다.
