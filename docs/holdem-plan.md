# 텍사스 홀덤 기획서

> 목표: 정해진 로직의 AI와 겨루는 **싱글플레이**, 그리고 사람끼리 붙는 **멀티플레이**.
> 이 문서는 구현 전 기획 단계 — 무엇을 만들지, 어떤 순서로, 무엇을 먼저 정해야 하는지.

## 확정 결정사항 (2026-07-21)

§11의 열린 질문에 대한 답이 확정됐다. 이후 모든 설계는 이 결정을 전제로 한다.

| 항목 | 결정 |
|---|---|
| 게임 방식 | **캐시게임** (토너먼트 아님 — 매 핸드 독립, 파산 시 리바이) |
| 싱글 인원 | **3인** — 나 + 초텐쨩 + 아메 |

| 놀이용 칩 | 게임 시작 시 **소량의 크레딧으로 구매**. 이 크레딧은 유료 결제가 아니라 운영자가 부여하는 재화라 사행성 문제 없음 (§6 참고, 방침 확정) |

## 0. 한 줄 요약

- **싱글**: 나 vs 초텐쨩 vs 아메 (3인 캐시게임, 고정 로직, LLM 안 씀) — **지금 만드는 것**
- **멀티**: 사람 vs 사람 최대 4인 (같은 방, 실시간 턴제) — **나중에**

## 1. 가장 먼저 짚을 것 — 기존 멀티 구조로는 홀덤을 못 만든다

이게 이 기획의 핵심입니다. 기존 대합전(퀴즈) 멀티는 **"호스트 권위" 모델**입니다:

- 호스트 클라이언트가 타이머를 돌리고, 라운드를 출제하고, **정답을 자기 브라우저에 들고** 있음 ([useMultiplayerRoom.ts](../src/hooks/useMultiplayerRoom.ts)의 `answerRef`)
- 서버(RPC)는 정답 검증만 대행. 게임의 "두뇌"는 호스트 브라우저에 있음
- 퀴즈에선 이게 괜찮음 — 최악의 부정이 "호스트가 정답을 안다" 정도라 김빠질 뿐 판이 안 깨짐

**홀덤에서 이 모델은 즉시 붕괴합니다:**

1. **히든 카드** — 홀덤은 각자 손패(hole cards)를 숨겨야 하는 게임. 호스트 클라이언트가 카드를 나눠주면 **호스트 플레이어가 전원의 패를 볼 수 있음**. 그 순간 게임이 무의미해짐.
2. **판돈** — 칩이 걸린 게임이라 부정 동기가 퀴즈와 비교할 수 없이 큼.
3. **브라우저는 신뢰할 수 없음** — 클라이언트에 있는 데이터는 콘솔에서 다 들여다볼 수 있음. 상대 패가 클라에 조금이라도 내려오면 끝.

> **결론: 멀티 홀덤은 반드시 "서버 권위(server-authoritative)" 모델이어야 한다.**
> 덱 셔플·손패·베팅 로직이 전부 서버(Postgres RPC 또는 Edge Function)에 살고,
> 각 플레이어는 **자기 손패만** 받아야 한다.

다행히 이 팀은 이미 이 패턴을 씁니다 — `mp_rounds` 테이블은 **RLS select 정책이 없어서** 클라가 직접 못 읽고, 오직 `security definer` RPC로만 접근합니다 ([014_multiplayer.sql](../supabase/migrations/014_multiplayer.sql):73). 홀덤의 손패도 **정확히 같은 원리**로 숨기면 됩니다. 새 개념이 아니라 이미 있는 무기를 확장하는 것.

**싱글은 이 문제가 없습니다** — 혼자 하니까 봇 패를 훔쳐봐도 자기만 손해. 그래서 싱글은 전부 클라이언트에서 돌려도 됩니다. 이 비대칭이 개발 순서를 결정합니다(싱글 먼저).

## 2. 포커 엔진 — 이 프로젝트의 크라운 주얼

싱글·멀티가 공유하는 **순수 함수 엔진**. 프레임워크 의존성 없이 짜야 브라우저(싱글)와 Deno Edge Function(멀티 서버) 양쪽에서 돌아갑니다.

```
reduce(state: HandState, action: Action): HandState
```

포함해야 할 것:

- **덱 & 셔플** — 52장, Fisher–Yates. 멀티에선 서버가 셔플(시드도 서버가 쥠).
- **핸드 진행** — preflop → flop → turn → river → showdown, 블라인드/버튼 이동.
- **베팅 라운드** — check/call/bet/raise/fold, 최소 레이즈 규칙, 올인.
- **사이드 팟** — 올인 플레이어가 여럿일 때 팟 분리. **여기가 버그의 온상**이니 테스트를 제일 촘촘히.
- **핸드 평가** — 7장 중 최고 5장 족보 판정 + 동점 처리(kicker). 이것도 순수 함수로 분리해 단독 테스트.

**핵심 원칙**: 엔진은 "누가 사람이고 누가 봇인지, 싱글인지 멀티인지" 전혀 몰라야 함. 그냥 상태와 액션만 안다. 이래야 한 번 만들어 네 곳(싱글 클라, 멀티 서버, 봇 사고용 시뮬, 테스트)에서 재사용됨.

**개발 리스크**: 포커 엔진은 "대충 되는" 것과 "정확한" 것의 간극이 큽니다. 특히 사이드 팟·동점·최소 레이즈. TDD가 사실상 필수 — 이 팀의 Superpowers 방법론과도 맞음. 여기에 시간을 제일 많이 써야 합니다.

## 3. 싱글플레이 (먼저 만든다)

- 전부 **클라이언트에서** 엔진 구동. 서버·실시간·비용 전부 0(칩 구매 RPC 한 번만 예외).
- **나 + 초텐쨩 + 아메 = 3인 테이블.** 캐릭터가 곧 상대이므로 봇 성격 부여(§5)가 이 게임의 재미를 좌우함.
- **캐시게임**이라 핸드마다 독립 — 누가 다 잃어도 게임 오버가 아니라 칩이 바닥나면 재구매(리바이) 흐름으로 이어감(§6).
- 판이 빠르게 도는 캐주얼 톤: 생각 시간 짧게, 애니메이션 가볍게.
- **이 단계에서 엔진·족보·UI가 다 검증되므로, 멀티는 "같은 엔진을 서버로 옮기는" 작업이 됨.**

## 4. 멀티플레이 (서버 권위) — 나중에, 최대 4인

**지금 단계에서는 착수하지 않는다.** 싱글로 재미가 검증된 뒤 별도로 설계·구현한다. 아래는 그때를 위한 밑그림만 남겨둠(인원만 4인으로 확정, 나머지는 미착수).

### 상태를 어디에 두나
- **권위 상태 = 서버**. `poker_tables` / `poker_seats` / `poker_hands`(손패, **RLS 없음**) 테이블.
- 손패 전달: `poker_get_my_hand` RPC가 `auth.uid()`의 카드만 반환. 남의 손패는 어떤 경로로도 클라에 안 내려감.
- 공개 상태(보드, 팟, 누구 차례, 베팅액)는 Realtime broadcast + 공개 뷰로 전원 동기화.

### 턴 진행
- 퀴즈는 "먼저 맞히기 레이스"였지만 홀덤은 **턴제** — 한 번에 한 명만 액션. 오히려 실시간 부하는 적음.
- 각 턴에 **행동 제한시간**(예: 20초). 시간 초과 시 자동 체크/폴드.

### 타임아웃/이탈 — 알려진 난제
- Postgres는 스스로 타이머를 못 돌림(이 팀이 이미 pg_cron 부재로 겪은 문제, [023 마이그레이션](../supabase/migrations/023_mp_cleanup_no_cron.sql) 참고).
- 그래서 턴 타임아웃을 **순수 서버 자동 진행으로 강제하기 어려움**. 현실적 절충안:
  - 각 플레이어 클라가 "지금 몇 초 지났다"를 보고, 초과 시 누구든 `poker_force_timeout` RPC 호출 → 서버가 **실제 경과시간을 재검증**한 뒤에만 자동 폴드 처리(클라 시계를 안 믿음).
  - 이러면 타이머 UI는 클라가, 판정은 서버가 → 부정 불가 + 진행 보장.
- 이 설계를 초반에 못 박아야 나중에 "판이 멈추는" 버그를 피함.

### 봇을 멀티에 넣을지 (선택)
- 이번 요청은 "싱글=봇, 멀티=사람"이라 **멀티 봇은 필수 아님**.
- 다만 봇 로직을 순수·이식 가능하게 짜두면, 나중에 **빈자리를 봇으로 채우는** 확장이 자연스러움 — 이건 이전에 라이어게임에서 지적한 "동접 부족" 문제를 푸는 공용 인프라가 됨. 지금 만들진 않되, 엔진·봇을 그 방향으로 열어두는 걸 권장.

## 5. 봇 AI — "정해진 로직" (LLM 안 씀)

매번 생성이 아니라 규칙 기반. 단계적으로:

1. **1단계 — 핸드 강도 기반**: 현재 족보/승률 근사 → 임계값으로 fold/call/raise. 프리플랍은 스타팅 핸드 등급표(예: 169칸 룩업)로 간단히.
2. **2단계 — 포지션·팟오즈**: 팟 오즈 대비 콜 여부, 버튼 근처면 공격적.
3. **3단계 — 성격 부여**: 봇마다 파라미터(공격성·블러프 빈도·타이트함)를 다르게 → 천사쨩/아메처럼 **캐릭터화**하면 재미와 IP를 동시에. "초텐쨩은 블러프쟁이", "아메는 타이트콜러" 식.

몬테카를로 승률 계산은 무겁지 않게(수백 회 시뮬이면 충분) 하거나, 사전 계산 테이블로 대체. **전부 순수 코드라 LLM 비용 0원** — 이 팀의 비용 민감도에 딱 맞는 게임입니다.

## 6. 칩·경제 — ⚠ 겜블링이 되면 안 됨 (하드 제약, 방침 확정)

**이건 타협 불가 설계 제약입니다.**

이 프로젝트의 크레딧은 유료 결제 재화가 아니라 **운영자가 부여하는 재화**다(현재 신규가입 지급 등, [007_signup_credits.sql](../supabase/migrations/007_signup_credits.sql)). 실제 현금 구매 경로가 없으므로 크레딧 자체를 판돈에 소량 소요시키는 것은 사행성 문제가 아니라는 데 동의했다. 단, **아래 경계는 여전히 지킨다** — 크레딧에 실제 결제 경로가 생기는 순간 이 설계는 재검토가 필요하다:

- **놀이용 칩(play chips)** 은 크레딧과 **별개의 잔고**로 관리한다(별도 테이블/컬럼). 게임 내에서 "칩→크레딧"으로 되돌리는 환전 경로는 만들지 않는다(편도 구매만 허용).
- **구매는 서버가 고정한 환율로만.** 클라이언트가 "이만큼 주세요"를 요청할 수 없고, `poker_buy_in()` RPC가 정해진 크레딧을 차감하고 정해진 칩을 지급한다(§9 1️⃣ 참고). 클라 조작으로 칩을 부풀릴 수 없게 함.
- **소량만 소요** — 한 판 buy-in에 크레딧 1~2 정도의 아주 적은 값으로 잡는다(실제 값은 §9 구현 시 확정). AI 생성처럼 "의미 있는 비용"이 아니라 입장 의식에 가까운 수준.
- 칩이 바닥나면 다시 `poker_buy_in()`으로 재구매(리바이) — 크레딧이 남아있는 한 반복 가능.
- 랭킹·업적이 생긴다면 칩 기준이 아니라 "승리 핸드 수" 등 게임 지표로 — 칩 액수 자체를 과시 지표로 키우지 않는다(칩 액수 경쟁은 도박적 동기를 자극하기 쉬움).

## 7. UI 스케치

- 기존 창(Window)·패널 스타일 재사용. 진입은 바다거북/설득처럼 **최소화 → 데스크탑 아이콘**.
- 테이블: 3석(나·초텐쨩·아메) 배치, 내 손패는 하단 크게, 보드 카드 중앙, 팟·베팅액 표시.
- 액션 바: Fold / Check·Call / Bet·Raise(+슬라이더).
- **카드 아트: 도트(픽셀) 스타일 확정.** 실제 그림 파일이 아니라 CSS/SVG로 픽셀 그리드 느낌(`image-rendering:pixelated`, 각진 픽셀 폰트)을 내는 방식으로 구현 — 설득게임 아이콘처럼 나중에 실제 도트 이미지로 교체 가능하게 열어둔다.
  - 배색은 기존 팔레트 재사용: 기본(초텐쨩 테이블)은 파스텔 핑크 계열(`--pink-*`, `--magenta`), `body.mode-ame`(아메 등장 시)는 다크 톤으로 자동 전환 — 이미 있는 변신 시스템을 그대로 탄다.
- 초텐쨩/아메 좌석에는 기존 Mascot 표정 이미지를 작게 배치해 베팅 반응(레이즈=공격적 표정, 폴드=시무룩 등)을 표현하면 캐릭터성이 살아남.
- 모바일 세로 대응: 3인이라 좌석 배치가 단순 — 상단에 상대 2명, 하단에 나.

## 8. 비용

- **싱글: 0원** (서버·LLM 없음).
- **멀티: LLM 0원.** 서버 비용은 Realtime broadcast + RPC 호출뿐 — 턴제라 트래픽도 낮음.
- 이 게임은 사실상 **무료로 운영되는 라인업**. 크레딧 소모처가 아니라 **리텐션/재미 담당**으로 자리매김.

## 9. 개발 단계 (진행 중 — 싱글까지)

Superpowers 방법론(Brainstorm→Plan→TDD) 기준. 각 단계가 독립적으로 "돌아가는 것"을 남기게 쪼갬. **아래는 이번에 실제로 진행하는 범위(싱글까지)이고, 멀티(§4)는 포함하지 않는다.**

1. **핸드 평가기** — 7장 최고5장 족보 + 동점. 순수 함수, 테스트 빡세게. (여기가 토대)
2. **핸드 진행 엔진** — 베팅 라운드·블라인드·사이드팟. 순수 함수, 테스트 빡세게.
3. **봇 AI 1단계** — 초텐쨩(블러프 성향)/아메(타이트) 성격 파라미터화, 핸드 강도 기반 결정.
4. **놀이용 칩 구매 RPC** — 서버 고정 환율로 크레딧→칩 편도 교환 (§6).
5. **싱글 UI + 도트 카드아트** — 사람이 실제로 한 판 돌려봄. **여기서 "재미있나"를 판단** (설득게임 교훈: 재미 판정을 최대한 앞으로).
